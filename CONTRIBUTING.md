# Contributing

Thanks for helping. This page covers everything you need to get a change merged.

## Setup

```bash
git clone https://github.com/SumitMandal/YOUR-REPO.git
cd YOUR-REPO
./scripts/install-hooks.sh
```

The hooks block commits to protected branches, bad branch names, secrets, large files and non-conventional commit messages. They only run on your machine: GitHub's web interface skips them, so the same branch-name and commit-message rules are checked again on every pull request.

## Branches

Start every change from `develop` (or from `main` for a hotfix):

```bash
git switch develop && git pull
git switch -c feature/short-description
```

| Prefix | Use for | Branch from | PR into |
| --- | --- | --- | --- |
| `feature/` | New work | `develop` | `develop` |
| `bugfix/` | A fix found in QA or on a release | `develop` or `release/x.y.z` | The same branch |
| `hotfix/` | An urgent production fix | `main` | `main`, and any open `release/x.y.z` |
| `backmerge/` | Resolving conflicts in a back-merge (maintainers) | `develop` | `develop` |
| `release/` | A version freeze (maintainers only, cut from `stage`, not a PR) | `stage` | `main` |

The prefix is lowercase; the rest may use letters (including an uppercase ticket key), digits, `.`, `_` and `-`: `feature/PROJ-142-partial-refunds`. GitHub's web interface suggests names like `username-patch-1` when you edit a file; change it to a name like `feature/PROJ-142-fix-typo`, or the `branch-policy` check fails. The branch must start with one of the prefixes above, so names generated by Jira or Bitbucket work, but GitLab-style issue branches such as `123-title` don't.

Promotion is done by maintainers:

- **`develop` → `stage`**: a pull request, merged with a merge commit.
- **Cutting a release**: create the branch from `stage` directly, not through a PR. Only maintainers and admins can create `release/*` branches:

  ```bash
  git fetch origin
  git push origin origin/stage:refs/heads/release/1.4.0
  ```

- **`release/x.y.z` → `main`**: a pull request, merged with a merge commit. Then tag `main` (only maintainers and admins can create `v*` tags) and open a back-merge PR from `main` into `develop`.
- **A hotfix while a release is open**: after the `hotfix/` PR merges into `main`, open a PR from `main` into the open `release/x.y.z` and merge it with a merge commit. (The hotfix branch itself is deleted automatically when it merges.)
- **A bug found on `stage`**: fix it on a `bugfix/` branch from `develop`, merge it there, and promote `develop` to `stage` again. A bug found on a release branch is fixed with a `bugfix/` PR into that release branch and reaches `develop` through the back-merge.
- **Back-merges into `develop` must use "Create a merge commit"**, never squash. Squashing them makes the branches' histories diverge and causes conflicts on every later promotion. If one is squashed by mistake, the `merge-guard` workflow fails, comments on the PR and says how to repair it.
- **Back-merge PR titles** must pass the title check too, so rename GitHub's default ("Main") to something like `chore: back-merge main into develop`. Promotion PRs likewise: `chore: promote develop to stage`, `chore(release): 1.4.0`.
- **Back-merge conflicts** can't be resolved in GitHub's web editor, because it would commit to `main`. Resolve them on a temporary branch instead:

  ```bash
  git fetch origin
  git switch -c backmerge/1.4.0 origin/develop
  git merge origin/main        # resolve conflicts, then sign the merge commit
  git push -u origin backmerge/1.4.0
  ```

  Open a PR from `backmerge/1.4.0` into `develop` and merge it with a merge commit. Conflicts on a `main` → `release/x.y.z` PR work the same way: branch `backmerge/…` from the release branch, merge `origin/main`, and open the PR into the release branch.

PRs into `stage`, `release/*` and `main` must come from branches in this repository, not forks. Changes under `.github/`, `githooks/` and `scripts/` always need a code owner's approval. In an emergency, an admin can merge a PR into any protected branch without meeting the rules; this is logged, and direct pushes stay blocked. Only admins can delete shipped `release/*` branches.

## Commits

Every commit on a `feature/`, `bugfix/` or `hotfix/` branch is checked by the required `commit-messages` check, because a merge commit keeps them all in the history. When you edit a file in GitHub's web interface, replace its default message (for example `Create test` or `Update README.md`) with a Conventional Commit. If a commit fails the check, reword it with `git rebase -i` and force-push your branch, or ask for the PR to be squash-merged, which keeps only the PR title.

Use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(api): add partial refund endpoint

Customers can now refund part of an order.

Closes #142
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Mark breaking changes with `!` (`feat(api)!: ...`) or a `BREAKING CHANGE:` footer. Keep the subject line to 72 characters or fewer.

`stage`, `release/*` and `main` require signed commits; `develop` doesn't. Commits GitHub creates when it merges a PR are signed for you, so squash-merged `feature/` and `bugfix/` PRs need no setup. A merge commit brings your own commits along, so **sign your commits** ([GitHub docs](https://docs.github.com/en/authentication/managing-commit-signature-verification/signing-commits)) on any branch that is merged with a merge commit: `hotfix/`, `backmerge/`, and `bugfix/` PRs into a release branch if not squashed. An unsigned commit there blocks the PR into `main`, or the next promotion into `stage`.

## Pull requests

1. Keep PRs small — under about 400 changed lines.
2. Fill in the PR template and link the issue (`Closes #123`).
3. Make CI green, then request review.
4. Reply to every comment and re-request review after changes.
5. The PR title must be a Conventional Commit of 72 characters or fewer (`feat(api): add partial refunds`), because merges use it as the commit subject. The merge dialog lets you edit the subject; leave it as the PR title.
6. **Feature and bugfix PRs into `develop` or `release/*` must be squash-merged.** `develop` also allows merge commits (for back-merges), but merging a feature PR that way brings its unsigned commits into `develop`, and the next `develop` → `stage` PR is blocked because `stage` requires signed commits. The `merge-guard` workflow flags this right after the merge.
7. PRs between long-lived branches (`develop` → `stage`, `release/*` → `main`, `main` → `release/*`, back-merges into `develop`) and hotfix PRs use merge commits.
8. GitHub's **Revert** button titles the new PR `Revert "feat: …"`, which fails the title check. Rename it to `revert: feat: …`.

Use the issue forms. For security issues, follow [SECURITY.md](SECURITY.md) instead of opening a public issue.
